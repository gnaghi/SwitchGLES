# ## SwitchGLES Code Audit Report\n\n### CRITICAL Issues\n\n**1. Viewport Y-flip inconsistency between `sgl_ensure_frame_ready` and `dk_apply_viewport`**\n- File: `/source/egl_impl.c` line 106-112 vs `/source/backend/deko3d/dk_state.c` line 51-56\n- Severity: CRITICAL\n- Category: Bug\n- Description: In `sgl_ensure_frame_ready()`, the viewport Y coordinate is manually flipped (`vp_dk_y = fb_height - viewport_y - viewport_height`), but in `dk_apply_viewport()` the viewport coordinates are passed through directly without any Y-flip. The code comment in `dk_apply_viewport` says \"DkDeviceFlags_OriginLowerLeft makes deko3d use GL-style coordinates [...] No manual Y-flip needed.\" This means the viewport set during frame acquisition at `sgl_ensure_frame_ready` uses a different coordinate convention than the viewport set during `sgl_prepare_draw`. The frame-start viewport will be wrong (inverted Y), though it gets overwritten by `sgl_prepare_draw` before the first draw call.\n- Suggested fix: Remove the Y-flip in `sgl_ensure_frame_ready` to match `dk_apply_viewport`. The `OriginLowerLeft` device flag handles it natively.\n\n**2. Scissor Y-flip inconsistency between `sgl_ensure_frame_ready` and `dk_apply_scissor`**\n- File: `/source/egl_impl.c` line 115-127 vs `/source/backend/deko3d/dk_state.c` line 65-107\n- Severity: CRITICAL\n- Category: Bug\n- Description: Same issue as the viewport. `sgl_ensure_frame_ready` manually Y-flips the scissor (`sc_sy = sc_fb_h - scissor_y - scissor_height`) while `dk_apply_scissor` passes through without flip. The frame-start scissor rect is inverted relative to what draw-time scissor would produce. If `glClear` is the first operation after frame start, it will use this incorrectly-flipped scissor (from `sgl_ensure_frame_ready`) rather than the correctly-unflipped scissor from `dk_apply_scissor` (which only runs during `sgl_prepare_draw`).\n- Suggested fix: Remove the Y-flip in `sgl_ensure_frame_ready` to match `dk_apply_scissor`.\n\n**3. Raw GPU command buffer pointer arithmetic in blend workaround**\n- File: `/source/backend/deko3d/dk_state.c` lines 153-161\n- Severity: CRITICAL\n- Category: Bug / Fragility\n- Description: The blend.dst workaround reads internal DkCmdBuf fields at hardcoded byte offsets (112 for `m_cmdPos`, 120 for `m_cmdEnd`). These offsets are specific to the current deko3d version's internal struct layout. If deko3d is updated or built with different compiler settings/alignment, the offsets will silently point to wrong fields, corrupting command buffer state and causing GPU hangs or rendering artifacts.\n- Suggested fix: Add a static assert or comment documenting which deko3d version/commit these offsets correspond to, and verify them. Ideally, upstream the fix to deko3d instead.\n\n### HIGH Issues\n\n**4. `glCopyTexImage2D` overwrites level-0 width/height even when `level > 0`**\n- File: `/source/gl/gl_texture.c` lines 780-783\n- Severity: HIGH\n- Category: Bug / Spec Violation\n- Description: `glCopyTexImage2D` always sets `tex->width = width; tex->height = height;` regardless of `level`. When called with `level > 0`, this overwrites the texture's base dimensions with the smaller mip dimensions, corrupting subsequent bounds checks in `glTexSubImage2D` and making the texture appear smaller than it is. Compare with `glTexImage2D` which only updates width/height at `level == 0`.\n- Suggested fix: Only set `tex->width` and `tex->height` when `level == 0`.\n\n**5. `glCompressedTexImage2D` always overwrites width/height regardless of mip level**\n- File: `/source/gl/gl_texture.c` lines 933-937\n- Severity: HIGH\n- Category: Bug\n- Description: Same issue as #4. `glCompressedTexImage2D` unconditionally sets `tex->width = width; tex->height = height;` even for `level > 0`, corrupting the GL-level tracking of the texture's base dimensions.\n- Suggested fix: Guard width/height updates with `if (level == 0)`.\n\n**6. `glDeleteTextures` does not check for FBO attachment collision between depth and stencil**\n- File: `/source/gl/gl_texture.c` lines 169-183\n- Severity: HIGH\n- Category: Bug\n- Description: If the same texture ID is attached as both `depth_attachment` and `stencil_attachment`, `fbo_ref_count` will be decremented twice but was only incremented once by `glFramebufferTexture2D`. This could cause `fbo_ref_count` to go negative, preventing proper deferred cleanup.\n- Suggested fix: Check if `fbo->depth_attachment == fbo->stencil_attachment` and only decrement once in that case.\n\n**7. `glGenTextures` partial allocation without rollback**\n- File: `/source/gl/gl_texture.c` lines 128-136\n- Severity: HIGH\n- Category: Bug / Spec Violation\n- Description: If allocating N textures fails partway through (e.g., texture 3 of 5 returns 0), the function sets `GL_OUT_OF_MEMORY` and returns, leaving textures 1 and 2 allocated but potentially orphaned (the caller doesn't know how many succeeded). Per GLES2 spec, `glGenTextures` should be atomic -- either all succeed or none.\n- Suggested fix: Track how many were allocated, free them on failure, and zero the output array.\n\n**8. Code memory never reclaimed for individual shaders**\n- File: `/source/backend/deko3d/dk_shader.c` lines 84, 148\n- Severity: HIGH\n- Category: Memory Leak\n- Description: Shader code memory uses a bump allocator (`dk->code_offset`). When individual shaders are deleted, the code memory is never returned -- it is only reset when ALL shaders AND ALL programs are deleted (`active_shader_count == 0 && active_program_count == 0`). In long-running applications that create and delete shaders incrementally (like dEQP), code memory grows monotonically and will eventually exhaust the 16MB pool.\n- Suggested fix: Implement a free-list for code memory (similar to the texture memory allocator) to reclaim individual shader slots.\n\n### MEDIUM Issues\n\n**9. `glCopyTexSubImage2D` bounds check uses base-level dimensions for all mip levels**\n- File: `/source/gl/gl_texture.c` lines 843-848\n- Severity: MEDIUM\n- Category: Bug / Spec Violation\n- Description: The bounds check compares `xoffset + width > tex->width` using the base-level dimensions directly, but when `level > 0` the actual mip-level dimensions are smaller. This allows writing past the mip level's boundaries without generating an error.
